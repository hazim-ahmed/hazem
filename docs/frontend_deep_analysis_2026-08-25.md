# تحليل شامل للفرونت اند - دفتر يوميات المصروفات

التاريخ: 2026-08-25  
النطاق: تحليل فقط لواجهة `apps/web` مع ملاحظة وجود نسخة موازية في `frontend`.  
المرجع الخلفي: عقد API الحالي في `docs/api_contract_expense_journal_frontend.md` ومسارات `apps/api/src/routes/index.ts`.

## 1. الخلاصة التنفيذية

الفرونت اند الحالي جيد كبداية تشغيلية لإدارة المصروفات اليومية: يوجد تسجيل دخول، لوحة يومية، نموذج إضافة مصروف، أرشيف يوميات، تفاصيل يومية، مشاريع، مستفيدون، تصنيفات، صناديق، مستخدمون، تقارير، وإعداد إلزامية المشروع. لكن كواجهة لدفتر يوميات رسمي يراجعه المحاسب ويوثقه ثم يطبع Excel/PDF، الواجهة ما زالت غير مكتملة.

أهم نتيجة: الواجهة تحتوي جزءاً من التسلسل المطلوب، لكنها تخلط بين:

- تسجيل مصروفات اليوم.
- إغلاق اليومية.
- اعتماد/توثيق اليومية.
- تصدير Excel/PDF.

حالياً لا توجد شاشة توثيق حقيقية، ولا توجد أزرار تصدير، وبعض أزرار الاعتماد تستدعي API غير موجودة.

## 2. هيكلة الفرونت الحالية

المشروع يحتوي واجهتين:

| المسار | الحالة | الملاحظة |
|---|---|---|
| `apps/web` | الواجهة الرسمية داخل monorepo | تستخدم `@expense-system/shared` ويجب اعتبارها المصدر الأساسي |
| `frontend` | نسخة موازية/قديمة أو بديلة | تحتوي نسخة `lib/shared` داخلها وقد تنحرف عن الرسمي |

التوصية: اعتماد `apps/web` فقط للمرحلة القادمة. وجود نسختين سيؤدي إلى تعديل شاشة في مكان ونسيان الأخرى، وهذا حدث فعلاً في تعديلات طريقة الدفع.

## 3. الصفحات الأساسية الموجودة

| الصفحة | الدور الحالي | التقييم |
|---|---|---|
| `/login` | تسجيل الدخول | مقبولة، فيها إظهار/إخفاء كلمة المرور ورسائل خطأ واضحة |
| `/dashboard` | يومية اليوم + جدول سندات اليوم + إضافة سريعة | مهمة لكنها مزدحمة وتكرر نموذج الإضافة |
| `/transactions/new` | نموذج إضافة مصروف كامل | أقرب شاشة صحيحة لتسجيل سند رسمي |
| `/journals` | أرشيف اليوميات | جيد كبداية، لكنه لا يعرض مرحلة مراجعة/توثيق واضحة |
| `/journals/[id]` | تفاصيل اليومية | صفحة المحاسب المفترضة، لكنها تستدعي مسارات اعتماد غير موجودة |
| `/reports` | مركز تقارير | جيد كفهرس، لكنه ليس تصديراً رسمياً |
| `/unassigned-projects` | ربط سندات بدون مشروع | مفيد للمراجعة قبل التوثيق |
| `/settings` | إعداد إلزامية المشروع | مفيد، لكن النص يذكر اعتماد/إغلاق غير مكتملين في الباك |
| `/projects`, `/beneficiaries`, `/categories`, `/cashboxes` | بيانات مساعدة | مناسبة كإدارة تشغيلية |

## 4. مطابقة الفرونت مع API

المسارات المستخدمة والمدعومة:

| مسار الفرونت | الحالة |
|---|---|
| `GET /today` | موجود |
| `GET /today/transactions` | موجود |
| `POST /today/transactions` | موجود |
| `PATCH /today/transactions/:id` | موجود |
| `DELETE /today/transactions/:id` | موجود |
| `GET /journals` | موجود |
| `GET /journals/:id` | موجود |
| `POST /journals/:id/close` | موجود |
| `POST /journals/:id/reopen` | موجود |
| `GET /payment-methods` | موجود |
| `PATCH /expense-transactions/bulk-assign-project` | موجود |

المسارات المستخدمة وغير الموجودة:

| مسار الفرونت | مكان الاستخدام | الأثر |
|---|---|---|
| `POST /journals/:id/approve` | `apps/web/app/journals/[id]/page.tsx` | زر اعتماد اليومية سيفشل |
| `POST /expense-transactions/:id/approve` | `apps/web/app/journals/[id]/page.tsx` | زر اعتماد السند سيفشل |

هذه أهم مشكلة فرونت حالياً، لأنها تجعل شاشة المحاسب تعرض أزراراً غير مدعومة من الباك.

## 5. تحليل تسلسل اليومية في الواجهة

التسلسل المطلوب حسب قرارك:

```text
12:00 صباحاً فتح يومية تلقائياً
↓
مسؤول الصرف يسجل المصروفات
↓
إغلاق تلقائي بعد نهاية اليوم
↓
المحاسب يراجع ويوثق
↓
النظام يجمد البيانات
↓
توليد Excel/PDF
↓
الختم اليدوي من المسؤول أو المدير المالي
```

ما يغطيه الفرونت حالياً:

- عرض يومية اليوم.
- تسجيل مصروف.
- تعديل/حذف مصروف من لوحة اليوم.
- عرض أرشيف اليوميات.
- عرض تفاصيل يومية.
- إغلاق/إعادة فتح يومية.

ما لا يغطيه:

- شاشة واضحة باسم “يوميات بانتظار مراجعة المحاسب”.
- حالة `PENDING_REVIEW` أو `DOCUMENTED` بصرياً.
- زر “توثيق اليومية” مدعوم فعلياً.
- شاشة مراجعة نهائية قبل التوثيق.
- تجميد الواجهة بعد التوثيق.
- توليد/تحميل Excel.
- توليد/تحميل PDF.
- تعليم اليومية كـ “تم الختم اليدوي” أو “تم رفعها للنظام الرئيسي”.

## 6. إضافة المصروف: النموذج الكامل مقابل السريع

حاليا توجد طريقتان:

- زر “إضافة مصروف سريع” داخل `/dashboard`.
- صفحة “النموذج الكامل” في `/transactions/new`.

بعد إضافة طريقة الدفع والملاحظات ومرجع التحويل، صار النموذجان يؤديان نفس الغرض تقريباً. هذا يسبب:

- تكرار منطق التحقق.
- تكرار جلب البيانات الأساسية.
- احتمال اختلاف سلوك الحفظ بين الشاشتين.
- تشتيت المستخدم: أين يسجل المصروف الرسمي؟

التوصية: إلغاء نافذة الإضافة السريعة والاعتماد على شاشة واحدة:

```text
/transactions/new
```

وتكون “سريعة ومنظمة” بدلاً من وجود نموذجين.

## 7. نموذج إضافة المصروف

نقاط القوة:

- يجلب يومية اليوم تلقائياً.
- يجلب المستفيدين والتصنيفات والمشاريع وطرق الدفع.
- يدعم مستفيد جديد بالاسم.
- يدعم طريقة الدفع.
- يطلب مرجع الدفع عند الحاجة.
- يدعم الملاحظات.
- يحترم إعداد `REQUIRED_ON_CREATE` للمشروع.

النواقص:

- لا يستخدم `react-hook-form` أو Zod في الواجهة رغم وجودهما في الاعتماديات.
- لا توجد ترجمة موحدة لأخطاء `VALIDATION_ERROR` القادمة من الباك.
- لا يعرض سبب إلزامية مرجع الدفع بجانب الحقل.
- لا يميز بين كاش وبنك بصرياً، رغم أن هذا مهم للمحاسب.
- لا يوجد منع واضح من الإدخال إذا كانت اليومية ليست `OPEN`.
- يرسل المستخدم إلى `/` بعد الحفظ، و`/` يعيد إلى `/dashboard` غالباً؛ الأفضل توجيه مباشر إلى `/dashboard` أو صفحة اليومية.

## 8. لوحة اليوم `/dashboard`

نقاط القوة:

- تعرض رقم اليومية وتاريخ النظام السعودي.
- تعرض إجمالي اليوم وعدد السندات.
- تعرض جدول السندات مع طريقة الدفع والملاحظات.
- تدعم تعديل وحذف سريعين.

النواقص:

- فيها “إضافة مصروف سريع” مكرر.
- تعديل السند لا يدعم حالياً طريقة الدفع أو الملاحظات أو الفاتورة، فقط المبلغ/الوصف/رقم السند.
- تستخدم `alert` و`confirm` بدلاً من Modal/Toast منسجم مع الواجهة.
- لا توجد معالجة واضحة لحالة تحميل الجدول أو فشل جلب البيانات.
- النص يقول “يومية مغلقة” لأي حالة ليست `OPEN`، وهذا لن يكفي عند إضافة `PENDING_REVIEW`, `DOCUMENTED`, `EXPORTED`.

## 9. صفحة تفاصيل اليومية `/journals/[id]`

هذه الصفحة يجب أن تصبح شاشة المحاسب الأساسية.

نقاط القوة:

- تعرض بيانات اليومية.
- تعرض جدول سندات مفصل.
- تعرض طريقة الدفع، مرجع الدفع، الفاتورة، الملاحظات، الحالة.
- تعرض أزرار إغلاق/إعادة فتح.

النواقص الحرجة:

- زر “اعتماد اليومية” يستدعي API غير موجودة.
- زر “اعتماد” للسند يستدعي API غير موجودة.
- زر “إضافة سند جديد” يرسل `journalId` في الرابط، لكن نموذج الإضافة الحالي لا يقرأ هذا `journalId`، والباك أصلاً يسجل في يومية اليوم فقط.
- الشريط السفلي `fixed bottom-0 right-64 left-0` قد يتداخل مع المحتوى ومع الشاشات الصغيرة.
- يعتمد على `journal.metrics`، بينما `JournalService.getJournalById` الحالي يرجع `totalAmount` و`transactionsCount` وليس `metrics` مفصلة، لذلك أرقام الشريط السفلي قد تظهر صفراً.
- لا توجد أزرار Excel/PDF.
- لا توجد خطوة توثيق رسمية.

## 10. أرشيف اليوميات `/journals`

نقاط القوة:

- يعرض رقم اليومية، التاريخ، الحالة، عدد العمليات، الإجمالي.
- يدعم عرض التفاصيل.
- يدعم إغلاق/إعادة فتح.

النواقص:

- لا يميز بين “مغلقة زمنياً” و“موثقة محاسبياً”.
- لا توجد فلاتر حسب الحالة أو التاريخ.
- لا يوجد عمود “وثق بواسطة” أو “تاريخ التوثيق”.
- لا يوجد عمود ملفات التصدير أو حالة الختم اليدوي.

## 11. التقارير

الفرونت يحتوي مركز تقارير وصفحات:

- سندات يدوية.
- فواتير معلقة.
- مصروفات حسب المشروع.
- سندات غير مرتبطة بمشروع.

نقاط القوة:

- مفيدة للمراجعة اليومية.
- صفحة السندات غير المرتبطة بالمشروع مهمة قبل التوثيق.

النواقص:

- ليست بديلة عن ملف Excel/PDF الرسمي.
- لا توجد صفحة “تقرير يومية جاهز للطباعة”.
- لا يوجد Preview قبل التصدير.
- لا توجد فلاتر تاريخية كافية في مركز التقارير.

## 12. الصلاحيات وتجربة الأدوار

الوضع الحالي:

- `Sidebar` يخفي المستخدمين والإعدادات عن غير `ADMIN`.
- باقي الصفحات الحساسة مثل إغلاق اليومية، إعادة فتحها، تعديل سند، حذف سند تظهر غالباً بدون تحقق واجهي حسب الدور.

المشكلة: الفرونت لا يترجم الأدوار المطلوبة للتسلسل:

| الدور | المطلوب واجهياً |
|---|---|
| مسؤول الصرف/CASHIER | يسجل مصروفات اليوم فقط |
| محاسب/ACCOUNTANT | يراجع ويوثق اليوميات |
| مدير مالي/MANAGER | يعتمد/يختم/يتابع التصدير |
| ADMIN | إعدادات وصلاحيات وإعادة فتح استثنائية |

التوصية: إضافة طبقة صلاحيات UI واضحة لكل Action، مع بقاء الباك هو المرجع النهائي.

## 13. تجربة المستخدم والتصميم

نقاط القوة:

- RTL مفعل.
- التصميم حديث وواضح في الواجهة الرسمية.
- استخدام جيد لـ React Query.
- استخدام أيقونات Lucide.
- النظام يعرض بيانات مالية مهمة مباشرة.

نقاط الضعف:

- اعتماد زائد على ألوان وتدرجات كبيرة في صفحات تشغيلية يفترض أن تكون أهدأ وأكثف.
- بعض الجداول كثيرة الأعمدة وقد تكون مرهقة على الجوال.
- اختلاف أسلوب التصميم بين الصفحات: بعضها “Bento/Fintech” وبعضها جداول بيضاء بسيطة.
- توجد عناصر زخرفية لا تضيف قيمة تشغيلية مثل `Sparkles` وعبارات `Pro`.
- أزرار خطرة مثل الحذف والإغلاق تستخدم `confirm` أو أزرار مباشرة دون شاشة سبب/توثيق.

## 14. إدارة الحالة والبيانات

نقاط القوة:

- React Query مستخدم بشكل جيد.
- Invalidations موجودة بعد الحفظ والتعديل.
- Axios interceptor يدعم refresh token.

النواقص:

- لا توجد طبقة API client منظمة؛ كل صفحة تكتب `api.get/post` بنفسها.
- لا توجد أنواع TypeScript قوية للـ DTOs؛ الاستخدام واسع لـ `any`.
- لا توجد مفاتيح Query موحدة.
- لا توجد Hook مثل `useTodayJournal`, `usePaymentMethods`, `useCreateExpense`.
- عدم استخدام الحزمة المشتركة في النماذج للتحقق في الواجهة.

## 15. مخاطر تقنية

| الخطورة | المشكلة | الأثر |
|---|---|---|
| عالية | أزرار اعتماد تستدعي API غير موجودة | فشل شاشة المحاسب |
| عالية | عدم وجود توثيق/تصدير Excel/PDF في الواجهة | التسلسل الرسمي غير مكتمل |
| عالية | ازدواجية `apps/web` و`frontend` | انحراف وتكرار عمل |
| متوسطة | نموذج سريع ونموذج كامل لنفس العملية | أخطاء صيانة وتجربة مربكة |
| متوسطة | أفعال خطرة بدون سبب إلزامي | ضعف الأثر الرقابي |
| متوسطة | استخدام `any` وندرة DTOs | أخطاء عقد API لا تظهر مبكراً |
| منخفضة | عدم اتساق بصري بين الصفحات | تجربة أقل احترافية |

## 16. توصيات ترتيب العمل

### الأولوية 1 - تثبيت مسار اليومية الرسمي

1. اعتماد `apps/web` فقط كواجهة رسمية.
2. إزالة أو تجاهل نسخة `frontend`.
3. إزالة “إضافة مصروف سريع” من لوحة اليوم.
4. جعل `/transactions/new` شاشة الإدخال الوحيدة.
5. تعديل صفحة تفاصيل اليومية لإزالة أزرار `approve` غير المدعومة مؤقتاً، أو تنفيذ API لها أولاً في الباك.

### الأولوية 2 - بناء شاشة المحاسب

1. صفحة “يوميات بانتظار المراجعة”.
2. صفحة مراجعة يومية تعرض كل السندات وإجماليات كاش/بنك.
3. زر “توثيق اليومية” بعد تحقق كامل.
4. منع التعديل بعد التوثيق.
5. سبب إلزامي عند إعادة الفتح.

### الأولوية 3 - التصدير الرسمي

1. أزرار توليد/تحميل Excel وPDF.
2. صفحة Preview قبل التصدير.
3. عرض حالة الملفات: تم التوليد، تم الختم، تم الرفع للنظام الرئيسي.
4. حفظ رقم النسخة وتاريخ التوليد في تفاصيل اليومية.

### الأولوية 4 - تحسين هندسة الفرونت

1. إنشاء `apps/web/lib/api/*` بدل استدعاءات API المباشرة داخل الصفحات.
2. تعريف DTOs للـ API.
3. Hooks لكل مجال: journal, transaction, project, paymentMethods.
4. استخدام Zod/React Hook Form في النماذج.
5. توحيد رسائل الأخطاء.

## 17. الحكم النهائي

الفرونت الحالي صالح كنموذج تشغيلي أولي، لكنه ليس جاهزاً بعد كواجهة دفتر يوميات رسمي للمحاسب. أكبر نواقصه ليست في الشكل، بل في التسلسل:

- لا توجد مرحلة مراجعة وتوثيق مكتملة.
- لا توجد صادرات Excel/PDF.
- توجد أزرار اعتماد غير متصلة بباك فعلي.
- يوجد تكرار بين نموذج سريع وكامل.
- يوجد خطر انحراف بسبب نسختي واجهة.

أفضل خطوة تالية: تنظيف مسار المصروفات ليصبح:

```text
لوحة اليوم للعرض فقط
↓
زر إضافة مصروف واحد
↓
صفحة إضافة مصروف رسمية
↓
أرشيف يوميات
↓
صفحة مراجعة محاسب
↓
توثيق + تصدير
```
